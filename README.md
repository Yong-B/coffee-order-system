# ☕ 커피숍 주문 시스템

> 포인트를 충전하여 커피를 주문하고, 최근 7일간의 주문 내역으로 인기 메뉴를 조회하는 시스템입니다.  
> 다중 인스턴스 환경에서도 포인트와 주문의 일관성을 유지하고, 주문 정보를 데이터 수집 플랫폼으로 전송하도록 설계합니다.

현재는 구현 전 설계 단계입니다. 아래 구조와 정책은 설계 검토 후 구현에 반영하며, 테스트 결과와 실행 방법은 구현 후 추가합니다.

## ✨ 핵심 기능

### 1. 커피 메뉴 목록 조회

- 메뉴 ID, 이름, 가격을 조회합니다.
- 메뉴 ID 오름차순으로 반환합니다.
- 메뉴가 없으면 빈 목록을 반환합니다.

### 2. 포인트 충전

- 사용자 ID와 충전금액을 입력받습니다.
- 1원은 1P이며, 양의 정수만 충전할 수 있습니다.
- 잔액 변경과 충전 이력을 같은 트랜잭션으로 저장합니다.

### 3. 커피 주문·결제

- 사용자 ID와 메뉴 ID를 입력받습니다.
- 보유 포인트에서 메뉴 가격을 차감합니다.
- 주문 생성, 포인트 차감, 결제 이력, 전송 이벤트를 하나의 트랜잭션으로 처리합니다.
- 주문 당시의 가격을 저장하여 이후 가격 변경으로부터 주문 내역을 보호합니다.

### 4. 주문 정보 전송

- 주문 커밋 직후 데이터 수집 플랫폼에 전송을 시도합니다.
- 사용자 ID, 메뉴 ID, 결제금액을 포함합니다.
- 전송 실패 시 저장된 이벤트를 재시도합니다.
- Mock API로 정상 전송, 실패, 중복 수신을 검증합니다.

### 5. 인기 메뉴 조회

- 최근 168시간의 주문 횟수가 많은 메뉴를 최대 3개 조회합니다.
- 주문 횟수가 같으면 메뉴 ID 오름차순으로 정렬합니다.
- 주문이 있는 메뉴만 반환합니다.

## 🔒 동시성 및 데이터 일관성

### 사용자별 DB 비관적 잠금

충전과 주문은 같은 회원의 잔액을 변경하므로 동일한 잠금 규칙을 적용합니다.

트랜잭션 내부에서 회원 행을 `SELECT ... FOR UPDATE`로 조회하여 같은 회원의 요청을 순차 처리합니다. 여러 인스턴스에서도 공유 DB의 잠금을 사용하므로 동일한 규칙이 적용됩니다.

| 대안 | 분석 및 선택 이유 |
| --- | --- |
| JVM 내부 잠금 | 다른 인스턴스의 요청을 제어할 수 없어 제외 |
| 낙관적 잠금 | 충돌 시 재시도 비용과 처리 정책 필요 |
| 조건부 UPDATE | 원자적 차감에 적합하나 이력·멱등성 처리도 함께 필요 |
| DB 비관적 잠금 | 잔액 확인부터 이력 저장까지 사용자별 직렬화가 명확하여 선택 |
| Redis 분산 잠금 | 별도 인프라와 잠금 만료·DB 커밋 간 조정이 필요하여 미도입 |

동일 회원의 처리량이 제한되는 대신 일관성을 확보합니다.
잠금 구간에 외부 HTTP 호출을 포함하지 않고, 잠금 대기 시간을 제한합니다.

### 트랜잭션 경계

다음 데이터는 함께 커밋하거나 함께 롤백합니다.

- 충전: 잔액 증가 + 충전 이력 + 멱등성 응답
- 주문: 잔액 차감 + 주문 + 결제 이력 + Outbox 이벤트 + 멱등성 응답

초기 잔액은 0이며 다음 불변식을 유지합니다.

```text
현재 잔액 = 충전금액 합계 - 결제금액 합계
```

### 중복 요청 방지

`(사용자 ID, 작업 종류, Idempotency-Key)` 조합을 고유하게 관리합니다.

- 같은 키와 같은 요청이면 최초 성공 상태 코드와 응답을 반환합니다.
- 같은 키에 다른 금액이나 메뉴를 전달하면 409를 반환합니다.
- 중복 여부는 회원 잠금을 획득한 뒤 확인합니다.
- 실패한 트랜잭션은 키 저장도 롤백하여 재시도를 허용합니다.
- 재응답의 잔액은 최초 처리 당시의 값입니다.
- 과제 범위에서는 성공한 요청의 키를 삭제하지 않습니다.

## 📤 외부 전송 안정성

### Transactional Outbox

외부 API와 DB를 하나의 로컬 트랜잭션으로 묶을 수 없으므로,
주문과 전송할 이벤트를 같은 DB 트랜잭션으로 저장합니다.

단순한 커밋 후 메모리 이벤트만 사용하면 서버 종료 시 전송 작업이 유실될 수 있습니다. Outbox는 미전송 작업을 DB에서 복구하기 위해 선택합니다.

### 전송과 복구

1. 커밋 직후 Worker 실행을 요청합니다.
2. Worker가 짧은 트랜잭션에서 이벤트를 선점합니다.
3. 처리 상태, 임대 토큰, 임대 만료 시각을 기록하고 커밋합니다.
4. DB 트랜잭션 밖에서 외부 HTTP 요청을 보냅니다.
5. 자신의 임대 토큰이 유효할 때 전송 결과를 갱신합니다.

다중 Worker의 작업 선점에는 `FOR UPDATE SKIP LOCKED`를 사용합니다.
별도 폴링으로 미전송 이벤트와 임대가 만료된 작업을 탐색합니다.

정상 환경에서 커밋 후 1초 이내 첫 시도를 목표로 하며, 실제 지연은 구현 후 측정합니다.

### 실패와 중복 전송

- 네트워크 오류, 타임아웃, 429, 5xx는 백오프를 적용해 재시도합니다.
- 최대 재시도 초과 또는 영구 오류는 FAILED로 보존합니다.
- 실패 원인을 수정한 뒤 같은 이벤트 ID로 재처리합니다.
- 전송 성공 후 DB 상태 갱신 전에 서버가 종료되면 중복 전송될 수 있습니다.

전달 방식은 at-least-once입니다.
수신 측은 `eventId`로 중복을 제거하고, 수신 기록과 처리를 원자적으로 저장해야 합니다.

### 전송 데이터

```json
{
  "eventId": "296ab273-16ce-48ef-8256-5d8c2f8503ea",
  "orderId": "d1865292-905a-478d-b952-c3c94b2f78eb",
  "memberId": 1,
  "menuId": 1,
  "paymentAmount": 3000,
  "paidAt": "2026-09-28T03:00:00Z"
}
```

외부 전송 실패는 이미 완료된 주문과 결제를 되돌리지 않습니다.

## 📊 인기 메뉴 집계 전략

정확성을 우선하여 Primary DB의 주문 원본을 직접 집계합니다.

| 항목 | 기준 |
| --- | --- |
| 기간 | 조회 기준 시각 직전 168시간 |
| 경계 | 시작 시각 포함, 종료 시각 제외 |
| 집계 대상 | 결제가 성공하여 저장된 주문 |
| 집계 단위 | 주문 한 건 = 1회 |
| 정렬 | 주문 횟수 내림차순, 메뉴 ID 오름차순 |
| 반환 개수 | 최대 3개 |
| 외부 전송 상태 | 집계에 영향 없음 |

기준 시각은 DB에서 한 번 산출하고, 범위와 집계 결과를 같은 SQL 문으로 조회합니다.
조회 SQL 시작 시 보이는 커밋 완료 주문을 기준으로 하며, 실행 중 커밋된 주문은 다음 조회에 반영됩니다.

`paid_at`은 주문 저장 단계의 DB 시각으로 기록하며 커밋 시각과 동일하다고 가정하지 않습니다.

캐시는 최신 주문 반영이 지연될 수 있어 초기 설계에서 제외합니다.
일별 집계만으로는 정확한 168시간 경계를 처리하기 어려워 원본 집계를 선택합니다.

`orders(paid_at, menu_id)` 인덱스를 적용하고, 데이터 증가 시 실행 계획과 조회 지연을 측정하여 최적화합니다.

## 🧪 테스트 계획

아래 항목은 구현 후 검증할 계획이며, 아직 실행한 결과가 아닙니다.

| 영역 | 검증 항목 |
| --- | --- |
| 메뉴 | 정상 조회, 정렬, 빈 목록 |
| 충전 | 정상 충전, 없는 회원, 잘못된 금액, 오버플로 |
| 주문 | 정상 결제, 잔액 부족, 없는 메뉴, 잔액 전액 사용 |
| 원자성 | 중간 저장 실패 시 잔액·주문·이력·이벤트 전체 롤백 |
| 멱등성 | 동일 키 반복·동시 요청의 단일 반영, 다른 본문 충돌 |
| 동시성 | 동시 충전, 동시 주문, 충전·주문 혼합 |
| 다중 인스턴스 | 두 애플리케이션에서 같은 회원에게 요청 |
| 외부 전송 | 정상 전송, 지연, 실패 재시도, 프로세스 종료 후 복구 |
| 중복 전송 | 동일 이벤트 재수신 시 Mock 처리 결과 한 건 |
| 인기 메뉴 | 168시간 경계, 동률, 빈 결과, 3개 미만, 정확한 횟수 |

DB 테스트는 실제 PostgreSQL을 사용합니다.
동시 요청에는 서로 다른 커넥션과 트랜잭션을 사용하며, 응답과 최종 DB 상태를 함께 검증합니다.

### 동시 주문 검증 예시

```text
초기 잔액: 10,000P
메뉴 가격: 1,000P
서로 다른 키를 가진 동시 주문: 20건

기대 결과:
- 성공 10건
- 잔액 부족 10건
- 최종 잔액 0P
- 주문·결제 이력·Outbox 이벤트 각각 10건
```

일시적인 잠금 실패는 동일 키로 제한적으로 재시도한 후 최종 결과를 판정합니다.
