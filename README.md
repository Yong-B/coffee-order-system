## ✨ 핵심 기능

### 1\. 커피 메뉴 목록 조회

- 메뉴 ID, 이름, 가격을 조회합니다.
- 메뉴 ID 오름차순으로 반환합니다.
- 등록된 메뉴가 없으면 빈 목록을 반환합니다.

### 2\. 포인트 충전

- 로그인한 회원의 식별값은 세션에서 확인합니다.
- 요청으로 충전금액을 전달합니다.
- 1원은 1P이며 양의 정수만 충전할 수 있습니다.
- 회원 행에 잠금을 획득한 뒤 잔액을 변경합니다.
- 충전 시 정수 범위를 초과하지 않도록 검증합니다.

### 3\. 커피 주문·결제

- 로그인한 회원이 메뉴 ID를 전달하여 주문합니다.
- 결제는 포인트로만 진행합니다.
- 잔액 확인, 포인트 차감, 주문 저장을 하나의 트랜잭션으로 처리합니다.
- 주문 당시의 결제금액을 저장하여 이후 메뉴 가격 변경과 분리합니다.

### 4\. 주문 정보 전송

- 주문 커밋 이후 데이터 수집 플랫폼 Mock API에 전송을 시도합니다.
- 사용자 ID, 메뉴 ID, 결제금액을 포함합니다.
- 외부 호출은 주문 트랜잭션 밖에서 수행합니다.
- 전송 실패와 이미 완료된 주문·결제는 구분하여 처리합니다.

### 5\. 인기 메뉴 조회

- 최근 7일간 주문 횟수가 많은 메뉴를 최대 3개 조회합니다.
- MySQL을 주문 원본으로 유지하고 Redis를 조회에 활용합니다.
- 주문 횟수가 같으면 메뉴 ID 오름차순으로 정렬합니다.
- 주문이 있는 메뉴만 반환합니다.

## 📋 구현 범위 및 정책

| 항목 | 정책 |
|---|---|
| 회원 등록 | SQL로 테스트 회원 등록 |
| 로그인 | loginId·password 확인 후 세션에 회원 ID 저장 |
| 회원가입·회원 관리 | 구현하지 않음 |
| 비밀번호 저장 | 로컬 학습용으로 평문 저장 |
| 메뉴 등록 | SQL로 초기 메뉴 등록 |
| 사용자 식별 | 충전·주문 시 로그인 세션에서 확인 |
| 주문 단위 | 주문 한 건당 메뉴 한 종류, 한 잔 |
| 결제 수단 | 포인트만 사용 |
| 초기 잔액 | 0P |
| 금액 | Java Long / MySQL BIGINT |
| 주문 취소·환불·재고 | 현재 범위에서 제외 |
| 시간 | UTC 기준으로 일관되게 저장·응답 |
| 최근 7일 | 조회 기준 시각 직전 168시간 |
| 요청 멱등성 | 기본 구현에서는 적용하지 않음 |
| 포인트 이력 테이블 | 기본 구현에서는 별도로 두지 않음 |
| Outbox·Kafka | 현재 범위에서 제외 |
| 테스트 | 이번 구현 범위에서는 작성·실행하지 않음 |

로그인은 핵심 과제 기능을 사용하기 위한 최소한의 사용자 구분 용도입니다.
인증 기능을 별도로 확장하지 않습니다.

평문 비밀번호 저장은 로컬 학습용 단순화이며 운영용 인증 설계가 아닙니다.

## 🎯 설계의 의도

### 핵심 업무에 집중

메뉴 조회, 포인트 충전, 주문·결제, 인기 메뉴 조회를 중심으로 구현합니다.
회원과 메뉴는 SQL로 등록하여 관리 기능의 범위를 줄입니다.

### 주문과 포인트의 일관성 유지

주문 생성과 포인트 차감은 하나의 업무로 취급합니다.
같은 트랜잭션으로 처리하여 주문만 생성되거나 포인트만 차감되는 상황을 방지합니다.

### 다중 인스턴스를 고려한 잔액 변경

프로세스 내부 잠금 대신 공유 MySQL의 행 잠금을 사용합니다.
서버 인스턴스가 달라도 같은 회원의 잔액 변경에 동일한 잠금 규칙을 적용하도록 설계합니다.

### 인기 메뉴 조회 부담 감소

반복되는 인기 메뉴 조회마다 주문 원본 전체를 집계하는 부담을 줄이기 위해 Redis를 활용합니다.
MySQL은 집계 결과 검증과 장애 복구의 기준이 되는 주문 원본을 보관합니다.

### 외부 연동과 주문 트랜잭션 분리

외부 플랫폼의 응답 지연이 포인트 잠금 시간을 늘리지 않도록,
주문 커밋 이후 외부 전송을 수행합니다.

## 🗃️ 데이터 모델

### members

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | BIGINT | 회원 ID, PK, AUTO\_INCREMENT |
| name | VARCHAR(100) | 회원 이름 |
| login\_id | VARCHAR(50) | 로그인 아이디, UNIQUE |
| password | VARCHAR(100) | 학습용 평문 비밀번호 |
| point\_balance | BIGINT | 현재 포인트 잔액, 기본값 0 |

### menus

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | BIGINT | 메뉴 ID, PK, AUTO\_INCREMENT |
| name | VARCHAR(100) | 메뉴 이름 |
| price | BIGINT | 메뉴 가격 |

### orders

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | BIGINT | 주문 ID, PK, AUTO\_INCREMENT |
| member\_id | BIGINT | 주문 회원 ID, FK |
| menu\_id | BIGINT | 주문 메뉴 ID, FK |
| payment\_amount | BIGINT | 주문 당시 결제금액 |
| paid\_at | DATETIME(6) | 결제 시각, UTC 기준 |

### 데이터 규칙

- 잔액은 0 이상이어야 합니다.
- 메뉴 가격과 결제금액은 양수여야 합니다.
- 결제가 성공한 주문만 저장합니다.
- 주문은 회원과 메뉴를 외래 키로 참조합니다.
- 회원과 메뉴의 물리 삭제 API는 제공하지 않습니다.
- 주문 당시 가격을 `payment_amount`로 보관합니다.
- 인기 메뉴 집계를 위해 `(paid_at, menu_id)` 인덱스를 둡니다.

MySQL의 `DATETIME`에는 타임존 정보가 저장되지 않으므로,
애플리케이션의 시간 처리와 JDBC 설정을 함께 맞춰 UTC 기준을 유지해야 합니다.

## 📡 API 명세

기본 경로는 `/api`이며 요청·응답은 JSON 형식입니다.
API 경로에 `v1`은 사용하지 않습니다.

충전과 주문에서는 요청으로 회원 ID를 받지 않고,
로그인 세션에 저장된 회원 ID를 사용합니다.

| 기능 | Method | URI | 성공 상태 |
|---|---|---|---|
| 로그인 | POST | `/api/members/login` | 200 |
| 메뉴 목록 조회 | GET | `/api/menus` | 200 |
| 포인트 충전 | POST | `/api/points/charges` | 200 |
| 주문·결제 | POST | `/api/orders` | 201 |
| 인기 메뉴 조회 | GET | `/api/menus/popular` | 200 |

아래 명세는 기본 구현의 목표 계약입니다.

### 1\. 로그인

```
POST /api/members/login
Content-Type: application/json
```

```
{
  "loginId": "member1",
  "password": "test1234"
}
```

성공 응답:

```
{
  "memberId": 1,
  "name": "테스트 회원",
  "pointBalance": 0
}
```

로그인 성공 시 세션에 회원 ID를 저장합니다.
후속 요청은 발급된 `JSESSIONID` 쿠키를 함께 전달합니다.
비밀번호는 응답에 포함하지 않습니다.

### 2\. 메뉴 목록 조회

```
GET /api/menus
```

성공 응답:

```
{
  "menus": [
    {
      "menuId": 1,
      "name": "아메리카노",
      "price": 3000
    },
    {
      "menuId": 2,
      "name": "카페라테",
      "price": 4000
    }
  ]
}
```

### 3\. 포인트 충전

```
POST /api/points/charges
Content-Type: application/json
```

```
{
  "amount": 10000
}
```

성공 응답:

```
{
  "memberId": 1,
  "chargedAmount": 10000,
  "balance": 10000
}
```

별도의 충전 이력 테이블은 없으므로 충전 이력 ID를 반환하지 않습니다.

### 4\. 주문·결제

```
POST /api/orders
Content-Type: application/json
```

```
{
  "menuId": 1
}
```

성공 응답:

```
{
  "orderId": 1,
  "memberId": 1,
  "menuId": 1,
  "paymentAmount": 3000,
  "remainingPoints": 7000,
  "paidAt": "2026-09-30T03:00:00Z"
}
```

성공 응답은 주문과 포인트 차감이 DB에 커밋되었음을 의미합니다.
외부 플랫폼의 수신 완료까지 의미하지는 않습니다.

### 5\. 인기 메뉴 조회

```
GET /api/menus/popular
```

성공 응답:

```
{
  "periodStart": "2026-09-23T03:00:00Z",
  "periodEnd": "2026-09-30T03:00:00Z",
  "menus": [
    {
      "menuId": 1,
      "name": "아메리카노",
      "price": 3000,
      "orderCount": 25
    },
    {
      "menuId": 2,
      "name": "카페라테",
      "price": 4000,
      "orderCount": 18
    }
  ]
}
```

- `periodStart`, `periodEnd`는 실제 집계에 사용한 범위입니다.
- 캐시된 결과라면 해당 결과를 계산한 기준 시각을 반환해야 합니다.
- `price`는 현재 메뉴 가격입니다.
- 집계 대상이 없으면 `menus`는 빈 배열입니다.
- 최신 주문 반영에 허용할 지연은 Redis 구현 전에 확정합니다.

### 오류 응답

공통 오류 응답의 목표 형식은 다음과 같습니다.

```
{
  "code": "INSUFFICIENT_POINTS",
  "message": "보유 포인트가 부족합니다."
}
```

| HTTP | 오류 코드 | 설명 |
|---|---|---|
| 400 | INVALID\_REQUEST | 필수 값 누락 또는 잘못된 입력 |
| 401 | LOGIN\_REQUIRED | 로그인 세션 없음 또는 만료 |
| 401 | LOGIN\_FAILED | 아이디 또는 비밀번호 불일치 |
| 404 | MEMBER\_NOT\_FOUND | 회원 없음 |
| 404 | MENU\_NOT\_FOUND | 메뉴 없음 |
| 409 | INSUFFICIENT\_POINTS | 잔액 부족 |
| 409 | POINT\_BALANCE\_LIMIT\_EXCEEDED | 충전 후 잔액 범위 초과 |
| 503 | TEMPORARILY\_UNAVAILABLE | 잠금 대기 초과 등 일시적 장애 |
| 500 | INTERNAL\_SERVER\_ERROR | 예상하지 못한 오류 |

공통 예외 처리 적용 전의 기본 Spring 오류 응답과는 다를 수 있습니다.

## 🔒 동시성 및 데이터 일관성

### 1\. 문제: 동시 요청으로 인한 잔액 오류

동일 회원의 요청이 동시에 잔액을 읽고 변경하면,
변경 내용이 덮어써지거나 보유 포인트를 초과한 주문이 승인될 수 있습니다.

### 대안 분석

| 대안 | 분석 |
|---|---|
| JVM 내부 잠금 | 한 프로세스 안에서만 공유되므로 다른 서버의 요청까지 제어할 수 없음 |
| 낙관적 잠금 | 충돌 감지가 가능하지만 실패 시 재시도 정책이 필요함 |
| 조건부 UPDATE | 원자적 차감이 가능하지만 실패 원인 구분과 후속 처리가 필요함 |
| DB 비관적 잠금 | 잔액 확인부터 변경까지 회원별로 순차 처리할 수 있음 |
| Redis 분산 잠금 | 잠금 만료와 MySQL 트랜잭션 종료 사이의 조정이 추가로 필요함 |

### 선택: 회원 행에 대한 DB 비관적 잠금

충전과 주문 모두 JPA의 `PESSIMISTIC_WRITE`를 이용한 회원 조회를 사용합니다.
잠금은 서비스의 트랜잭션 내부에서 획득합니다.

모든 잔액 변경 경로가 같은 잠금 정책을 따라야 합니다.
같은 회원의 요청은 대기할 수 있지만 다른 회원의 요청은 별도 행에서 처리합니다.

Redis는 인기 메뉴 조회에 사용하며, 포인트 변경의 잠금 용도로 사용하지 않습니다.

### 2\. 문제: 주문과 포인트 차감의 부분 성공

포인트를 차감한 뒤 주문 저장에 실패하면 잔액만 감소할 수 있습니다.

### 선택: 단일 DB 트랜잭션

포인트 차감과 주문 저장을 하나의 `@Transactional` 서비스에서 처리합니다.
중간 단계에서 실패하면 전체 DB 변경을 롤백합니다.

```
충전: 잔액 증가

주문: 잔액 차감 + 주문 저장
```

포인트 이력, 요청 멱등성, Outbox 저장은 현재 트랜잭션 범위에 포함하지 않습니다.

### 적용 시 고려사항

- 외부 HTTP 호출은 잠금 구간에서 제외합니다.
- 잔액은 잠금을 획득한 뒤 확인합니다.
- 세션에는 회원 ID만 보관하고, 잔액은 DB에서 조회합니다.
- 잠금 대기 시간에 상한을 두는 방향으로 구현합니다.
- `READ COMMITTED` 적용을 설계 방향으로 두며 실제 설정 여부는 별도로 확인합니다.

## 📊 인기 메뉴 조회 설계

### 설계의 의도

최근 7일간 인기 메뉴를 반복 조회할 때 발생하는 DB 집계 부담을 줄이기 위해 Redis를 활용합니다.

MySQL에는 결제 완료 주문 원본을 유지하고,
Redis 데이터가 유실되더라도 원본으로 다시 구성할 수 있도록 설계합니다.

### 집계 정책

- 최근 7일은 조회 기준 시각 직전 168시간입니다.
- 시작 시각은 포함하고 종료 시각은 제외합니다.
- 결제가 성공한 주문만 집계합니다.
- 주문 한 건을 주문 횟수 1회로 계산합니다.
- 주문 횟수 내림차순, 메뉴 ID 오름차순으로 정렬합니다.
- 주문이 있는 메뉴를 최대 3개 반환합니다.
- 외부 플랫폼 전송 성공 여부는 집계에 영향을 주지 않습니다.

### 저장소별 역할

| 저장소 | 역할 |
|---|---|
| MySQL | 결제 완료 주문 원본 및 집계 복구 기준 |
| Redis | 인기 메뉴 조회에 사용할 순위·주문 횟수 데이터 |

### 문제해결 전략 및 대안 분석

| 후보 방식 | 장점 | 해결할 문제 |
|---|---|---|
| MySQL 집계 결과를 Redis에 캐싱 | 주문 원본 기준으로 계산하고 복구하기 쉬움 | 갱신 사이 최신 주문과 시간 경계가 즉시 반영되지 않음 |
| 주문 완료 시 Redis에 반영 | 주문 발생에 따라 빠르게 갱신 가능 | 중복·누락 반영, DB와 Redis 사이의 장애, 기간 만료 처리 |

Redis 점수를 계속 증가시키는 방식만으로는 최근 7일 집계가 되지 않습니다.
168시간이 지난 주문을 제외하고 동일 주문의 중복 반영도 방지해야 합니다.

일별 집계 7개를 단순 합산하는 방식 역시 조회 시각 직전 168시간과
범위가 다를 수 있으므로 그대로 적용하지 않습니다.

### 확정 사항

- 인기 메뉴 조회에 Redis를 사용합니다.
- MySQL을 주문 원본으로 유지합니다.
- 메뉴별 주문 횟수의 정확성을 요구합니다.

### 구현 전 확정할 사항

- 최신 주문 반영에 허용할 지연
- Redis 자료구조 및 키 구성
- 집계 갱신 방식
- 중복·누락 반영 방지
- 168시간이 지난 주문 제외 방식
- 동률 정렬 방식
- Redis 장애 시 조회 정책
- 복구 중 조회 결과의 일관성

Redis 도입은 결정했지만 세부 전략은 아직 확정하지 않았습니다.
집계 기준 시각에 대한 정확성과 최신 주문의 반영 시점은 구분하여 정의합니다.

## 📤 주문 정보 외부 전송

### 선택: 커밋 후 Mock API 호출

주문 트랜잭션 안에서 Spring 이벤트를 발행하고,
`@TransactionalEventListener(AFTER_COMMIT)`로 커밋 이후 전송을 시도하는 방식으로 시작합니다.

이벤트에는 주문 시점의 사용자 ID, 메뉴 ID, 결제금액을 담습니다.
리스너에서 지연 로딩이 필요한 엔티티에 의존하지 않도록 값을 전달합니다.

### 선택 이유

- 외부 응답 지연 동안 회원 행 잠금이 유지되는 것을 피합니다.
- 롤백된 주문을 외부 플랫폼에 전송하지 않습니다.
- 추가 메시지 브로커 없이 기본 전송 기능을 구현합니다.

`AFTER_COMMIT`은 실행 시점을 의미하며, 그 자체로 비동기 실행을 보장하지 않습니다.
별도 비동기 처리를 적용하지 않으면 외부 호출이 API 응답을 지연시킬 수 있으므로 타임아웃을 설정합니다.

### 전송 데이터 예시

```
{
  "orderId": 1,
  "memberId": 1,
  "menuId": 1,
  "paymentAmount": 3000,
  "paidAt": "2026-09-30T03:00:00Z"
}
```

### 실패 처리와 한계

- 외부 전송 실패는 별도로 기록합니다.
- 이미 커밋된 주문과 포인트 차감을 되돌리지 않습니다.
- 외부 전송 실패를 주문 결제 실패로 오인하게 하지 않도록 응답 정책을 분리합니다.
- 커밋 직후 프로세스가 종료되면 이벤트가 유실될 수 있습니다.
- 전송 실패에 대한 영속적인 재시도는 현재 보장하지 않습니다.

Kafka와 Transactional Outbox는 현재 도입하지 않습니다.

## 🧩 기술적 선택 이유

### Spring Boot / Spring Web MVC

REST API와 애플리케이션 설정을 구성하고,
메뉴·포인트·주문 업무 로직에 집중하기 위해 사용합니다.

### Spring Data JPA

엔티티 중심으로 DB에 접근하고 트랜잭션 내 변경을 관리합니다.
회원 잔액 변경에는 비관적 잠금을 적용하는 방향으로 설계합니다.

### MySQL InnoDB

트랜잭션, 외래 키, 행 잠금을 사용하여 주문과 회원 데이터의 관계 및 일관성을 관리합니다.

### Redis

반복적인 인기 메뉴 조회에 활용합니다.
DB 집계 부담 감소를 목표로 도입하되,
실제 성능 개선이 측정된 상태는 아닙니다.

### Long / BIGINT

포인트는 정수 단위로 처리하므로 부동소수점 타입을 사용하지 않습니다.
양수 검증과 충전 시 오버플로 검사를 함께 적용합니다.

### Bean Validation

필수 값 누락과 잘못된 금액 등 요청 형식의 오류를 검증합니다.
잔액 부족과 같은 업무 규칙은 서비스·도메인에서 검증합니다.

### HttpSession

토큰 발급 구조를 추가하지 않고 최소 로그인 기능을 제공하기 위해 사용합니다.
세션에는 회원 ID만 저장합니다.

### Kafka 미도입

현재는 필수 API와 DB 트랜잭션 구현에 집중합니다.
외부 플랫폼 전송은 커밋 후 직접 호출하는 방식으로 시작합니다.

### SQL 기반 스키마 관리

현재는 DDL과 초기 데이터 SQL을 직접 적용합니다.
Flyway는 도입하지 않았습니다.

## ⚠️ 현재 범위의 한계

### 다중 인스턴스의 로그인 상태

DB 행 잠금은 다중 인스턴스의 잔액 변경을 고려한 설계입니다.
하지만 기본 HttpSession은 서버 메모리에 저장되므로,
다른 인스턴스에서 로그인 상태가 자동으로 공유되지는 않습니다.

인기 메뉴용 Redis를 도입하는 것만으로 세션이 공유되는 것은 아닙니다.
따라서 현재 전체 애플리케이션이 다중 인스턴스 요구사항을 모두 충족했다고 주장하지 않습니다.

### 중복 요청

충전·주문에 요청 멱등성을 적용하지 않습니다.
응답 유실 후 같은 요청을 다시 보내면 중복 충전·주문이 발생할 수 있습니다.
회원 행 잠금은 동시 잔액 변경을 제어하지만 중복 요청 자체를 제거하지는 않습니다.

### 포인트 이력

별도 충전·차감 이력 테이블을 두지 않습니다.
현재 잔액과 주문 내역은 저장하지만, 모든 충전 내역을 추적할 수는 없습니다.

### 외부 전송

커밋 후 직접 전송은 장애 시 이벤트 유실과 전송 실패 복구를 보장하지 않습니다.

### Redis 집계

자료구조와 갱신 정책이 아직 확정되지 않았으므로,
최근 168시간 집계의 정확성과 최신성은 구현 단계에서 구체화해야 합니다.
